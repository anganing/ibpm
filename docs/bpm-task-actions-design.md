# BPM 审批操作动态禁用方案

> 初稿日期：2026-09-26；加签、减签专项复核：2026-10-06。工作区：`D:\iboot-pro\ibpm`。
> 状态：方案评审稿，已核对项目代码、Warm-Flow 1.8.9 源码并执行离线引擎探针，尚未实施或完成宿主运行验收。
> 本次目标：通过、驳回、加签、减签根据当前任务动态启用，前端提示与后端执行使用同一套判定。

## 1. 建议采用的规则

按钮可用条件 = 当前用户具备该任务办理资格 + 任务仍可办理 + 当前节点允许该操作 + 本次操作满足运行条件。

判定的主键是 `taskId`。节点从该任务的 `definitionId + nodeCode` 取得，使用实例正在运行的定义版本。不能使用同一 flowCode 的最新版本，不能用实例概览中的 nodeCode 代替任务节点，并行任务可能属于不同节点。

| 操作 | 节点条件 | 运行条件 | 禁用提示示例 |
|---|---|---|---|
| 通过 | 有可供 PASS 使用的流程路径 | 当前用户仍是办理人、任务有效 | 当前任务已处理 / 当前节点未配置通过路径 |
| 驳回 | 明确配置 REJECT 路径，或配置有效的 anyNodeSkip 退回目标 | 当前用户仍是办理人、任务有效，路由无歧义 | 当前节点未配置驳回路径 |
| 加签 | 节点扩展属性显式允许 ADD_SIGN | 任务有效，可选择合法且尚未在当前待办人员中的用户 | 当前节点未允许加签 |
| 减签 | 节点扩展属性显式允许 REDUCE_SIGN | 存在可移除的当前办理人，移除后至少保留一名有效办理人 | 当前任务仅剩一名办理人，不能减签 |

通过和驳回的能力优先从路由推导，不额外增加一个会与路由冲突的“允许驳回”开关。加减签通过节点扩展属性表达业务授权，因为引擎自身的加减签 API 不会自动读取业务按钮开关。

加签表示增加当前任务的办理人，不会自动把或签改成会签。或签中一人通过就可能完成节点；希望新增人员也必须审批，应在流程定义中配置会签。节点签署方式继续由原定义控制，不由按钮代码偷偷修改。

本方案的加签是“在当前节点增加参与人”。先让新增人员审批再回原审批人、原审批人同意后再让新增人员审批，属于前加签/后加签的顺序语义；不能把当前增加人员 API 宣称为已支持这些模式。

## 3. 设计器配置

实现业务侧 `BpmNodeExtServiceImpl implements NodeExtService`，在节点属性中增加“审批操作”复选项。初始交付只提供已经接入完整业务接口的 ADD_SIGN、REDUCE_SIGN。

建议固定扩展项 code 为 `bpm_task_actions`，选项值采用业务动作枚举，避免复用官方示例中含义不明确的数字。保存形态沿用插件原生 ext 数组：

```json
[
  { "code": "bpm_task_actions", "value": "ADD_SIGN,REDUCE_SIGN" }
]
```

业务端读取已保存的 ext，不修改插件 JAR、第三方资源或引擎表结构。与其他扩展项共存，不覆盖整个 ext。

- 没有该项或值为空：加减签均不允许。
- 明确配置对应动作：继续检查任务和人员条件，不能仅凭该值启用。
- 老定义仍按路由开放通过、驳回，加减签默认关闭；在新版本中配置后生效，已有实例继续使用旧版本。
- 通过与驳回不直接采用上述列表；它们按流程路径确定。这样配置一个复选框不会凭空创造驳回路径。

## 4. 驳回路径判定

1. 读取任务及对应定义版本、当前节点、节点出线和目标节点。
2. 如果配置了 anyNodeSkip，先校验该目标存在且符合引擎限制。配置无效时提示定义有误，不默默退化为其他路径。
3. 没有 anyNodeSkip 时，要求当前节点存在明确 REJECT 出线及有效目标。
4. 没有上述配置时禁用驳回。不能把 PASS 出线、空 skipType 出线、流程中任意一个历史节点当作驳回授权。
5. 如存在可能抢先匹配的空类型出线，禁用普通驳回并提示“当前节点跳转类型配置不明确”；通过新定义版本修正。不能显示允许后再让引擎随机选择。
6. 使用引擎节点查询能力核对目标和网关规则，不通过调用 skip/reject 再回滚来试探能力。

发布校验补充：人工审批节点的正常出线要求明确 PASS/REJECT，同一动作的直接出线不依赖“取第一条”决定业务分支；条件分流通过网关表达。开始节点、网关自身的空跳转类型按引擎规则处理，不能一刀切禁止所有空 skipType。

兼容现有定义：旧定义若仅有空类型路径，可暂按引擎现有规则保留通过能力，但不把该路径开放为驳回。新版本发布时要求显式配置。仅图上无退回线不足以认定不支持驳回，还需核对 anyNodeSkip。

普通驳回、退回上一步、指定节点退回是不同操作。此次保留普通驳回语义，不在没有路由时偷偷调用 rejectLast/rejectAtWill。未来增加目标选择时，单独定义动作与服务端可选目标集合。

能力接口返回当前可确定的节点配置、资格及运行限制。条件网关最终匹配和监听器效果仍由提交时的引擎决定，能力响应不承诺提前执行完整流程；前端保留提交失败提示和刷新入口。

## 5. 后端接口与共用判定

新增 `TaskActionPolicyService`，读取配置并产生每个动作的 `enabled`、`reasonCode`、`reason`。能力查询和写接口共用它，前端不得提交 canReject 一类字段来决定权限。

建议新增 `GET /admin/approval/task/{id}/actions`，沿用项目统一响应包装。以下仅为 data 内容示例：

```json
{
  "taskId": "任务ID",
  "instanceId": "实例ID",
  "actions": {
    "APPROVE": { "enabled": true, "reasonCode": null, "reason": null },
    "REJECT": { "enabled": false, "reasonCode": "NO_REJECT_ROUTE", "reason": "当前节点未配置驳回路径" },
    "ADD_SIGN": { "enabled": false, "reasonCode": "ACTION_NOT_CONFIGURED", "reason": "当前节点未允许加签" },
    "REDUCE_SIGN": { "enabled": false, "reasonCode": "LAST_HANDLER", "reason": "当前任务仅剩一名办理人，不能减签" }
  }
}
```

查询先做用户和实例可见性校验，非授权用户不能通过 taskId 枚举人员和配置。查看资格与办理资格分别判断；详情可看不代表动作可用。

新增写接口：

| 接口 | 请求体 | 执行 |
|---|---|---|
| `POST /admin/approval/task/{id}/add-sign` | `{ userIds: string[], message: string }` | 校验后调用 addSignature |
| `POST /admin/approval/task/{id}/reduce-sign` | `{ userIds: string[], message: string }` | 校验后调用 reductionSignature |

当前登录用户作为 handler，忽略权限校验的开关不向前端开放。既有 approve/reject 接口也增加相同策略复核。

对象校验：加签 ID 去重且非空，用户存在且可用，排除已经在当前任务待办集合中的人；减签对象必须仍在当前任务可移除集合中，去重后计算移除结果，至少保留一名有效办理人。已有任务只有一名办理人时，可以在允许加签的节点加人，但不能减签。

候选人员通过受任务资格保护的查询接口返回：加签候选来自 common 的 `UserApi.listSimple/isEnabled`，减签候选来自当前任务仍未办理的人员，并补齐姓名。不能选择已经办理完、其他任务或其他节点的人员。提交时重新核对，不能信任抽屉打开时的旧集合。当前人员均为 APPROVAL，后续转办可覆盖 TRANSFER；委派人员不混入可移除集合。

加减签、通过、驳回均在事务中执行，并共用互斥入口。考虑到撤销/终止会处理整个实例，建议统一实例维度的锁，取得锁后重新读取任务与人员集合，避免两次各自合法的减签最终把人全部减完，也避免生命周期操作和单个任务审批互相穿透。实现时优先复用项目现有锁设施。

## 6. 前端交互

- 打开待办详情时按当前 taskId 拉取 actions；能力未返回或失败时按钮保持禁用，并提供重试。只读详情不请求办理能力。
- “通过、驳回、加签、减签”根据 actions 渲染禁用状态，悬停展示服务端返回的业务原因。关闭按钮一直可用。
- 用户不具备办理资格时保持只读；不能因为超级管理员身份就自动取得任务办理资格。
- 使用项目统一 `a-drawer`，不新增小弹窗。加签抽屉选择可用用户；减签抽屉只列出当前可移除人员，并告知至少保留一人。两者展示当前节点、签署方式、人员和操作意见。
- 或签加签提示“增加可办理人员，任一人通过仍可推进”；会签加签提示“新增人员加入当前会签，剩余参与人需全部通过”。
- 加减签成功后重新拉取人员、任务能力和待办列表。引擎仅改变人员、保留协作历史，不自动推进节点，不应显示“审批通过”或直接当作流程完成。减成一人也要由剩余人员正式办理。
- 减掉当前操作者并非引擎禁止的操作；若产品允许且移除后仍有有效办理人，成功后当前用户退出办理态，不能继续保留可提交的审批按钮。
- 通过或驳回提交成功后沿用现有刷新行为。任务已被别人处理时关闭办理态并刷新列表。
- 使用现有打开序号防止旧请求覆盖新任务，所有写操作提交期间禁用其他动作，防止重复点击。

## 7. 加减签上线前必须补的验证

### 7.1 当前或签、会签范围与人数计算

静态源码发现：`TaskServiceImpl#updateHandler` 将加减签记录写为 NONE；`cooperate` 在 765—769 行调用 `HisTaskService.listByTaskId`，以待办数量加所有历史记录数量计算 allNum。`HisTaskServiceImpl#listByTaskId`（50 行）未按协作类型筛选。

2026-10-06 DBX 只读复核：当前人工节点只有 `nodeRatio=0` 和 `100`。0 共 72 个，其中已发布 32 个；100 共 2 个，其中已发布 1 个。当前 flow_user 46 条均为类型 1，尚无 TRANSFER/DEPUTE 存量人员。首期重点覆盖或签与会签，不为当前未使用的比例票签扩大实现范围。

或签在 `TaskServiceImpl` 743–744 行直接返回正常流转；加签不能改变其一人办理即可推进的含义。100 会签中 NONE 会增大分母，但 825–827 行有最后一名待办正常流转的分支；760–761 行优先处理会签驳回。因此不能仅凭分母增加认定当前会签卡死，仍应核对真实完成时机。

举例：两人会签加一人，存在三条待办与一条 NONE 历史。计算分母为 4，三轮通过比例可能为 25%、50%、75%；最后一人仍因剩余待办为一而进入正常流转。减签后剩一人不会由 `reductionSignature` 自动审批；剩余人随后通过时才正常流转。

当前代表性回归应验证：或签加人仍一人流转、会签加人等待新增人员、有人已经通过后再加减签、减到一人继续办理、会签驳回，以及并发减签不产生无人任务。不能把源码核对或离线协作分支探针当作宿主端到端验收。

未来使用比例票签或依赖 allNum 的表达式时，再专项验证“3 人、60% 通过率、两人同意”在加签前后的差异。若确认问题，应修正实际计票口径或采用已核实的官方修复；不能删协作历史、篡改 nodeRatio、设置 ignore 跳过协作来绕过。需要变更依赖时遵循项目依赖管理规定。

### 7.2 历史动作和审批结论

项目当前 lastSkipType 查询只排除了开始节点，会取到最新 NONE 协作记录。这与“最近动作”的原始契约一致，不能全局随意改成过滤 NONE。展示协作历史时使用 cooperateType；判断最终审批结果时明确选取终审的 PASS/REJECT 记录，校验现有终态回调不会把加减签当作终审。

当前已办把每条历史映射为 taskId，前端同样用 taskId 作行 key。加减签后操作者再审批会产生同任务多条历史，必须增加 historyId 作为记录行标识，不能通过 taskId 去重而丢失操作历史。加减签协作类型分别为 6/7，skipType 为 NONE。

### 7.3 转办和委派的后续接入

它们可以复用同一节点扩展配置和动作策略，但要完成配套链路再开放：当前待办、详情可见性、handle 都主要检查 APPROVAL 类型，转办产生 TRANSFER、委派产生 DEPUTE；仅调用引擎 API 会导致接收者缺失待办或被业务接口拒绝。受托人提交还会先回到委托人，不等同于正常审批流转，应有单独的交互文案。

本次明确交付通过、驳回、加签、减签；转办和委派在上述链路完整前不出现在可选配置中。撤销、终止、抄送按各自业务用途单独接入，不能因引擎支持就自动开放。

## 8. 实施顺序与验收

| 顺序 | 交付内容 | 验收依据 |
|---|---|---|
| 1 | 驳回路径判定、actions 接口、现有 approve/reject 后端复核、详情按钮禁用 | 无退回路径时 UI 不可点，直接接口也拒绝；有合法退回路径时可办理 |
| 2 | 节点扩展项及发布校验 | 设计器保存重开配置不丢失；新旧定义版本互不串用 |
| 3 | 加减签引擎行为验证、业务接口、选人、任务锁 | 加签人数正确、减签至少剩一人、审批投票结果正确 |
| 4 | 前端交互与整体联调 | 操作后状态及时刷新；原有发起、通过、驳回、已办、只读详情保持正确 |

必要案例：

- 单审批节点仅 PASS 到结束：驳回禁用，通过可用。
- 当前节点有 REJECT 到有效目标：驳回可用，结果落到定义的目标。
- 没有 REJECT 线但配置有效 anyNodeSkip：按配置支持退回。
- 空 skipType 与 REJECT 混用、退回目标失效：给出定义配置原因，写接口同样拦截。
- 节点未配置加减签：按钮禁用，绕过前端的请求被拒绝。
- 单人任务允许加签后新增第二人；当前只有一人时不能减签；一次移除全部人员被拒绝。
- 新增用户实际能在待办中找到并办理任务；移除用户不能继续办理。
- 当前或签、会签分别验证加减签后的参与人数和结束时机；比例票签启用时再专项验收。
- 有人已经会签通过后，剩余办理人加签/减签，已有审批记录保留，按当前剩余正式参与人继续办理。
- 减签之后仅剩一人时不自动推进，剩余人能够完成；允许减掉自己时，自己待办消失、不能继续办理。
- 任务已办、非办理人、旧版本实例、并行不同节点、宿主暂停新发起时的在途任务判定正确。
- 两个并发减签/审批请求不会产生无人办理或重复完成。
